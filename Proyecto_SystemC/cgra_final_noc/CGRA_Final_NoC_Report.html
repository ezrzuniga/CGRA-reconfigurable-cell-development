CGRA_Final_NoC_Mesh — connections & verification

Same 3×3 layout and the same five synthesizable cells as the direct-wire CGRA_Final_Mesh — Memoria, Vectorial, Escalar, two Routing relays, four MAC. The interconnect underneath is different: nine NoC_Router instances forward header-addressed packets instead of driving fixed point-to-point wires.

Figure 1 — physical connections of the 3×3 mesh

Every grid position holds a compute cell and a router, co-located. Cells never talk to each other directly anymore — each cell's four ports feed its own router's local ports, and routers talk to their neighbors over packet links. Only the boundary ports actually exercised by the three testbenches below are drawn, labeled with their real signal names.

Figure 2 — how one router decides where a packet goes

This is the part a labeled box can't show: NoC_Router is combinational (no clock edge of its own, same discipline as Routing_Cell) — it reads a header on every input every cycle and re-decides the output ports from scratch.

Scope & known limitations

  • No input buffering or credit-based flow control — a losing arbitration candidate is dropped that cycle. Real CGRA traffic never triggers this (every packet is consumed at the first router it reaches); only the synthetic router test forces it, on purpose.
  • NoC_Router::route() is combinational, like Routing_Cell — a multi-hop packet can ripple through several routers inside one clock edge rather than being pipelined. That trade keeps this fabric cycle-accurate-identical to the direct-wire mesh; a real ASIC NoC would normally pipeline each hop.
  • Boundary destination tagging is a fixed rule (dest = the entry router's own position), not a programmable routing table — this is still an application-specific mesh, not a general-purpose NoC.
